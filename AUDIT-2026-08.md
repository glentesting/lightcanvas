# LightCanvas Audit — August 21, 2026

Read-only audit of the repo against its new mission: a personal tool for one user to
design, preview, and export a working `.loredit` (LOR S6) show for his own hardware
by November. All findings below are from reading and running the code, not from docs.

---

## Verdict

The core is worth keeping: the timeline editor, per-pixel render engine, audio
analysis, photo-based night preview, and Zustand store are genuinely real, and a
rewrite would burn weeks reproducing them. But the two things that matter most for
the goal — a `.loredit` export and an AI that actually sequences a full song — **do
not exist today**: there is zero `.loredit` code anywhere (the only LOR exporter
writes S4-era `.lms`, flattens every prop to a single RGB triple, and isn't even
reachable from the UI), and the AI path sends the model a thumbnail of the music and
caps out around 60–100 sparse blocks. Keep the foundation, delete the ~20% SaaS
shell, and treat the `.loredit` exporter and the AI density redesign as new builds —
that is faster than a rewrite, but nobody should mistake it for "mostly done."

## What actually works

Verified by reading the code (and running build/type-check):

- **Timeline editor** (`/timeline`, `src/components/Timeline*`): real drag-and-drop
  effect blocks, beat snapping, undo/redo (zundo), keyboard shortcuts, autosave.
- **Render engine** (`src/lib/render/engine.ts`): the crown jewel. Pure function
  `renderFrame(sequence, fixtures, t)` → per-pixel RGB for every fixture, with
  geometry-aware effects (strand-by-strand mega-tree chases, matrix rows). All three
  preview surfaces share it.
- **Audio analysis** (`src/lib/audio/beat-detector.ts`): real client-side DSP —
  spectral-flux onsets, BPM autocorrelation with octave correction, RMS loudness,
  section detection. Crude (naive 64-bin DFT, fixed threshold, rigid metronome beat
  grid that ignores tempo drift) but not faked.
- **Photo night-stage preview** (`NightStage` + `src/lib/scene/photo-depth-scene.ts`):
  real three.js — uploaded house photo, client-side depth estimation (Depth Anything
  V2), night grading, bloom, per-pixel light points driven live by `renderFrame`.
- **Persistence**: Supabase project CRUD, audio upload, autosave, depth-map caching —
  all real server routes.
- **Importers** (`src/lib/imports/xsq.ts`, `lor.ts`): real DOMParser-based parsers
  for xLights `.xsq` and LOR `.lms`, with RGB channel grouping.
- **AI generation endpoint** (`/api/ai/generate` + `anthropic-provider.ts`): real SSE
  stream, real Anthropic call (`claude-sonnet-4-6`) when the key is set, zod
  validation with per-block salvage, blocks patched live into the editor store.
- **Export code as code** (`src/lib/exports/`): the xLights `.xsq` ZIP packager, `.lms`
  generator, LightCanvas JSON round-trip, hand-rolled ZIP writer, and video (WebM)
  capture are all genuinely implemented — with the fatal caveats in the LOR section.

## LOR export status — the headline finding

**A working `.loredit` export does not exist. It is not partially built. There is
no trace of the format anywhere in the codebase.** Verified directly: zero grep hits
for `loredit`, `saveFileVersion`, or any S5/S6 sequence structure in `src/`.

What does exist, in `src/lib/exports/lor.ts` (387 lines):

- An **`.lms` (S4-era) XML generator**. It writes `<sequence><channels><channel
  deviceType="LOR" unit circuit>` with effect elements in centiseconds, ZIPped with
  the audio and a README.
- **It flattens every fixture to one RGB channel triple** (3 LOR channels: Red,
  Green, Blue) regardless of pixel count. A 100-pixel mini tree becomes a single
  color. All per-pixel motion — chases on arches, tree spirals, stake waves — is
  discarded at export; chase literally degrades to "solid intensity" (its own code
  comment admits this).
- Even this exporter is **unreachable from the UI** (orphaned ExportDialog), and the
  server-side `/api/export` route doesn't support LOR at all.

What this means for the actual hardware (2× Pixie16, ~1,200 pixels, 16-channel AC
controller, N4-G4 Director):

- For the **AC controller** (roofline/ridges/peaks), `.lms`-style single-channel
  intensity output is roughly the right shape — S6 can open and convert legacy
  `.lms` files. Salvageable as a concept, not as the deliverable.
- For the **pixel props**, the current export model is architecturally wrong, not
  just incomplete. S6 sequences pixels via props defined in an S6 Preview with
  motion-effect rows (or thousands of per-pixel channels). None of the concepts a
  `.loredit` needs — Previews, props, Pixie16 unit/port addressing, motion effect
  rows, saveFileVersion 15 structure — exist anywhere in this codebase.
- The **xLights `.xsq` exporter is real but irrelevant** to this hardware: the
  Director can't play FSEQ, and `.xsq` is an editor project file, not a player file.

Bottom line: the `.loredit` exporter is a **from-scratch build**, and it is the
single largest technical risk in the whole plan — the format is complex, poorly
documented, and the only acceptance test is "S6 v6.6.12 opens it and it plays."

## AI pipeline status

End-to-end trace (all real files, real calls — with real problems):

1. **Audio in**: MP3 uploads to Supabase; analysis runs **in the browser** on the
   raw file (`beat-detector.ts`). Real DSP, but the beat grid is a fixed `60/BPM`
   metronome fitted to a phase offset — it does not track tempo drift, so a live or
   rubato recording drifts out of sync over 3–4 minutes. If analysis throws, the
   error is swallowed and the project proceeds without it.
2. **Prompt**: single user message to `claude-sonnet-4-6` (`max_tokens: 8192`, no
   system prompt, no retry). It contains duration, BPM, section list, fixture list,
   style hints — and **only the first 20 beat timestamps**. Onsets, downbeats,
   loudness envelope, and spectral features are computed and shipped to the server,
   then **never enter the prompt**. The model cannot align to actual beats past
   ~10 seconds; it extrapolates a grid.
3. **Response**: JSON array → zod validation with per-block salvage → filtered to
   known fixtures/time bounds. Reasonable. But truncation (`stop_reason:
   max_tokens`) is unhandled — a long response dies as "AI returned invalid JSON."
4. **Into the editor**: blocks stream back over SSE in batches of 4 and are applied
   to the Zustand store with undo tracking. This part is solid.
5. **The fakery**: with no API key, users silently get `MockAIProvider`, complete
   with fake `sleep(800)` "Listening to song..." theater. Ironically the mock is a
   deterministic sequencer that uses the **full** beat list, downbeats, and loudness
   envelope — more of the music than the real AI path sees.

**Would it produce a dense, synced 3–4 minute show for ~20 props? No.** The prompt
floor is `max(10, fixtures×3)` blocks (~60 for 20 props — one block per prop per
minute), and 8,192 output tokens caps it around 60–100 blocks with no
chunking-by-section, no continuation, and no post-hoc beat snapping. The mock
produces several hundred blocks for the same input. The pipeline's plumbing (SSE,
validation, store patching) is reusable; the prompting/chunking strategy needs a
redesign, not a tweak.

## Visualizer status

Three render surfaces, one shared engine — light *states* are real everywhere;
drawing fidelity varies:

1. **Photo night-stage** (the shipping preview when a photo exists): real three.js.
   Depth-displaced photo plane, night-grade shader, bloom, and **one point per
   physical pixel** driven live by `renderFrame` + the transport clock. Pixel
   ordering deliberately matches the effect renderers (strand-correct mega-trees,
   per-pixel arch beziers). This genuinely previews sequence output.
2. **SVG house fallback** (no photo): real data in, decorative out — all pixels of a
   fixture averaged to one color, all fixtures of a kind collapsed to one slot.
   Effectively a mood light, and explicitly labeled legacy in the code.
3. **Visualizer V2 prototype** (the untracked work): Canvas2D photographic
   compositor — night plate, surface spill, halos, bulb cores. Nice output, but a
   **sealed sandbox**: only reachable at `/dev/visualizer-v2` (404s in production),
   driven entirely by hardcoded demo fixtures with a hand-traced roofline and a
   synthetic 24-second looping sequence. No store, no audio, no project. The
   component itself calls the real `renderFrame` and could accept real data;
   nothing feeds it any.

**The real gap is geometry, not effects.** The layout editor stores exactly one
drag-anchor point per prop with hardcoded default sizes. The engine supports
multi-point traced polylines (how the v2 demo gets its convincing roofline), but
**no UI exists to trace them** — so an actual user's roofline renders as a straight
horizontal line, and prop shapes are idealized defaults, not his props.

   *Today:* works. Upload, BPM, onsets, sections are real. The rigid beat grid is

3. **AI produces a dense, musically-synced full-song sequence.**
   *Today:* plumbing real, output toy-scale (~60–100 sparse blocks, 20 beats of
   actual music context, silent mock fallback). Needs a chunk-by-section redesign
   with the full beat/energy data and post-snap. Half there.
4. **The preview honestly shows what the yard will do.**
   *Today:* the strongest asset. Photo night-stage renders true per-pixel sequence
   output. Needs prop-shape fidelity (roofline tracing UI exists in the engine but
   not the UI). Mostly there.
5. **A `.loredit` file that S6 v6.6.12 opens and the Director plays.**
   *Today:* **0%. Does not exist in any form.** The only LOR code writes S4 `.lms`,
   destroys pixel data, and is unreachable from the UI. This is the critical path
   and the biggest unknown — it needs format reverse-engineering against real S6
   files from his own setup, started immediately, with "S6 opens it" as the weekly
   test. If it slips, the fallback is exporting per-prop intensity data S6 can
   convert and doing pixel motion effects inside S6 by hand — which he would have
   to learn anyway for network config and Director SD creation.

Twelve weeks is enough **only if** the `.loredit` exporter starts now and everything
cosmetic is ignored. The order that matters: (1) exporter spike against a real S6
sample file, (2) prop/channel mapping for his exact hardware, (3) AI density
redesign, (4) roofline/shape tracing. Everything else in this repo is either done
enough or doesn't matter anymore.
